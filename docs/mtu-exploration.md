# MTU exploration (unreleased)

Branch `experiment/rx-mtu-auto` starts from the v0.2.0 release commit.
Its automatic mode is not included in the published v0.2.0 package.

## Prototype

`rx_segment_mtu=0` selects the current Thunderbolt netdev MTU for each completed
RX aggregate. Nonzero values retain `min(interface MTU, cap)`. The default and
packaged example remain 1500. The setting itself is read-only after module
load; interface MTU changes are observed without reloading the driver.
A READ_ONCE snapshot is used for each aggregate; an aggregate racing a change
can use the old snapshot. No addresses, bridges or interface MTUs are changed
by the driver.

This controls inferred GSO segment size. It does not recover the sender's MSS
or discover the eventual bridge port, route MTU or remote path MTU.
A 9000-byte ingress MTU is not proof that 9000-byte segments fit an egress.
Do not enable automatic mode on mixed-MTU production forwarding yet.

## Isolated forwarding results — 2026-10-10

[CI run 38018167718](https://github.com/riverscn/thunderbolt-net-dkms/actions/runs/38018167718)
tested commit `1564702` on Linux `6.8.0-146-generic`,
`6.12.111+deb13-amd64` and `7.0.0-38-generic`. All three builds, kernel tests,
DKMS lifecycle checks and their configured regression tests passed.
The per-case MTU observations were identical across all three kernels.

The diskless QEMU guests have no external NIC or Thunderbolt controller.
They run 39 packet unit tests, 16 bridge/router controls and 80 MTU/PMTU
observations per kernel, plus GRO ordering and driver load/unload checks.
The MTU matrix uses real Linux Bridge/IP forwarding with synthetic ingress
and egress devices, IPv4/IPv6, and receive GRO on/off. MTUs change on the
same live devices without reloading the test module. Large fixtures carry
20,001 TCP payload bytes; IPv4 has DF set. The software egress advertises no
TSO, so any output segments are generated by the kernel.

| Ingress / egress MTU | Route MTU | Cap | Result |
| --- | --- | ---: | --- |
| 1500 / 1500 | Interface-derived | 0 | Valid bridge/routed output, maximum IP length 1500 |
| 9000 / 9000 | Interface-derived | 0 | Valid bridge/routed output, maximum IP length 9000 |
| 9000 / 1500 | Interface-derived | 0 | Bridge emits three oversized frames; routing returns MTU 1500 feedback with no TCP output |
| 9000 / 1500 | Interface-derived | 1500 | Valid bridge/routed output, maximum IP length 1500 |
| 1280 / 1280, then 1500 / 1500 | Interface-derived | 0 | Valid output follows live interface MTU |
| 9000 / 9000 | 1500 | 0 | MTU 1500 feedback, no TCP output |
| 9000 / 9000 | 1500 | 1500 or 1280 | Valid routed output within route MTU |
| 9000 / 9000 | 1280 | 0 or 1500 | MTU 1280 feedback, no TCP output |
| 9000 / 9000 | 1280 | 1280 | Valid routed output within route MTU |

The 1200-byte-payload controls pass with automatic mode over both explicit
route MTUs (IP lengths 1240 for IPv4 and 1260 for IPv6). This confirms those
paths can carry small packets; it does not demonstrate TCP PMTU recovery.

Per kernel, 60 observations forward complete payloads with correct sequence
numbers/checksums and no oversized output, four bridge observations emit
oversized frames, and 16 routed observations return PMTU feedback without TCP
output. The [240-row dataset](mtu-results.csv) records each observation;
these are not 240 successful forwarding cases.

The captured responses are IPv4 Fragmentation Needed and IPv6 Packet Too Big.
Their advertised MTUs match the forwarding limits, and quoted TCP ports and
sequence offsets match the original aggregate or its generated segments,
including sequence wraparound. Explicit IPv6 route limits can produce one
response per segment: three for cap 0/9000 and fourteen for cap 1500. The
isolated guest disables ICMP rate limiting to make this observable; these
counts are not predictions for production systems. Quote checks do not
validate the ICMP checksum or a sender's processing of the response.

The software sink intentionally accepts oversized frames for inspection.
Reaching its transmit callback is not proof of successful wire transmission:
a real NIC/peer may reject them. These are synthetic packet-path observations,
not complete TCP/PMTUD sessions or physical-device performance measurements.

## Decision and remaining work

Keep automatic mode experimental and retain the default 1500 cap. Ingress MTU
tracking works, but neither it nor the bridge master MTU establishes every
forwarding limit. Even a 1500 cap is not sufficient for a 1280 route: the cap
must fit the intended path. The published v0.2.0 package is unchanged.

Before selecting an automatic forwarding policy, test complete TCP sessions
and sender reaction to PMTU feedback, then VLAN and offload-capable egress
paths. Linux emitting a correct error does not establish that macOS adjusts
its Thunderbolt aggregates, or that this driver can recover their original
MSS. Real Thunderbolt throughput and hotplug validation remain separate;
no host driver or network configuration was changed for these experiments.
